The Portiloop Field Console

The Portiloop Field Console is an add-on, written outside the Portiloop project, that turns a Portiloop and a laptop into a wake EEG setup: the Portiloop streams its signals over the network, and the laptop plays the sounds, records everything and analyses it. This tutorial explains how it works and how to set up and run a session with it: the Portiloop settings, installation, the signal check, the calibrations, the mismatch negativity and resting-state tasks, the files and the analyses.

What the Field Console is

The add-on lives in its own repository, TomsCoder/Portiloop-Field-Console, under the internal name TMDA-PAV. Its README describes the release as follows:

"This `eLife` branch contains only the tasks and analyses used for the published data: sensation-level (SL) calibration, computer audio-latency calibration, active (with practice) and passive gap-deviant MMN, and eyes-closed resting state, recorded through the experiment console, sequencer, and Portiloop signal check; and MMN amplitude/latency, obligatory P1-N1-P2 responses, active-MMN behavior, and resting-state analyses, plus the EEG montage/reference and audio-latency correction utilities."README.md, lines 23 to 29 [1]

(The repository on GitHub has a single branch, named main; the README still speaks of an "eLife" branch.) In practice it is a set of Python programs for a laptop:

  • experiment_console.py: the experimenter console (a PySide6 window) that holds the identifiers, the audio devices, the calibrations, and launches every task and analysis;
  • portiloop_setup.py: the signal-quality console (live traces, spectra, montage, guided checks);
  • the tasks: sl_task.py (sensation level), audio_latency_task.py, resting_state.py, oddball_active_training.py, oddball_active.py, oddball_passive.py, all built on one recording engine, oddball_paradigm_with_lsl.py;
  • the analyses: mne_analysis.py, mmn_standard_erp_analysis.py, mmn_behavior_analysis.py, and two utilities, eeg_montage.py and update_audio_latency.py (README lines 37 to 58 [1]).

How it differs from an overnight recording

In tutorials 01 to 05 the Portiloop does everything by itself: it records to its SD card, detects slow oscillations and plays the sounds. With the Field Console the Portiloop is only the amplifier. It sends its samples over its own Wi-Fi network with the Lab Streaming Layer (LSL, an open protocol that streams time-stamped samples between programs and computers), and the laptop does the rest.

What the Portiloop v2.3 publishes

When "Stream LSL" is checked in the Advanced tab of the Control Center (tutorial 03), the recording process creates up to three LSL streams when you press Start. Their definitions are in the Portiloop software:

class LSLStreamer:
    def __init__(self, streams, channel_count, frequency, id):
        ...
        lsl_info_raw = StreamInfo(name='Portiloop Raw Data',
                                  type='eeg',
                                  channel_count=channel_count,
                                  nominal_srate=frequency,
                                  channel_format='float32',
                                  source_id=id)
        ...
        if streams['filtered']:
            lsl_info = StreamInfo(name='Portiloop Filtered', ...)
        ...
        if streams['markers']:
            lsl_markers_info = StreamInfo(name='Portiloop_stimuli',
                                          type='Markers', ...)

Each new sample is pushed as soon as the recording loop receives it from the acquisition process (capture.py, lines 446 to 449; the streamer is created only if "Stream LSL" is checked, lines 243 to 247). The raw values are in microvolts, the same as the raw_ch columns of the CSV (tutorial 05). The Portiloop does not attach channel names to the stream: a receiver sees "ch1" to "ch8".

The Field Console uses only "Portiloop Raw Data": the name is a constant, TARGET_LSL_STREAM = "Portiloop Raw Data" (tmda_pav/config/montage.py, line 14), and it ignores the filtered stream and the Portiloop's markers. It opens the stream with LSL clock synchronisation, de-jittering and monotonic timestamps (pylsl.proc_clocksync | pylsl.proc_dejitter | pylsl.proc_monotonize, tmda_pav/recording/lsl.py, lines 62 to 100), so that the EEG timestamps are expressed in the laptop's clock, the same clock used to time the sounds and key presses. Its own event markers go to a separate stream that it creates, "OddballMarkers", and they are also written into the FIF file.

Finding the stream on the Portiloop's Wi-FiLSL normally discovers streams by multicast, which some networks block. The add-on ships a file lsl_api.cfg with two lines, [lab] and KnownPeers = 192.168.4.1: 192.168.4.1 is the Portiloop's address on its own network (tutorial 03), and "KnownPeers" is "a list of known computers to query directly" [3]. The LSL library looks for lsl_api.cfg first in the file named by the LSLAPICFG environment variable, then in the current directory, then in ~/lsl_api/lsl_api.cfg, then in /etc/lsl_api/lsl_api.cfg [4]. The experiment console starts every task from the repository folder (subprocess.Popen(command, cwd=SCRIPT_DIR)), so the file is found there; if you start a script from another folder, or use the standalone signal check (below) in another folder, copy the file next to it or into ~/lsl_api/.

Setting up the Portiloop for a wake session

The add-on's documentation does not say how to configure the Portiloop. The steps below are what the Portiloop v2.3 code requires for the stream to exist and to contain what the add-on expects; they are our recommendation, not the add-on author's.

  1. Power on and connect the laptop to the Portiloop's Wi-Fi. As for the phone in tutorial 03; open http://192.168.4.1:8081/ on the laptop or on a phone. The laptop is then on the Portiloop's network, which has no internet access: install everything beforehand.
  2. Place the electrodes and run the Check tab with all of them connected. An electrode that is OFF at the last check is switched off in the next recording and records zeros (tutorial 03); the add-on's signal check would then report it as "flat or frozen".
  3. Advanced tab: Pipeline "Acquisition only". This pipeline has no filter, detector or stimulator (custom_pipelines.py, lines 10 to 15), so the Portiloop never plays a sound of its own. Do not leave a sleep pipeline in Cond B: after the "Stimulation starts after" delay the Portiloop would start stimulating through its own audio output.
  4. Check "Stream LSL" (simple_gui.py, line 735). Keeping "Save recording locally" checked as well gives an independent CSV backup on the SD card (tutorial 05). The sample frequency is read from the stream by the add-on; it does not ask for a particular value. We assume the default 250 Hz.
  5. Press Start. The LSL stream exists only while the Portiloop is recording; when you press Stop it disappears, and the add-on reports that "Portiloop Raw Data" was not found. Keep the Portiloop recording for the whole session.

Installation

The add-on is a set of scripts, not an installable package: clone it and install its dependencies. The README gives the full installation as python -m pip install -r requirements.txt (line 611). requirements.txt lists numpy, scipy, pandas, matplotlib, mne, fooof (>=1.1.1,<2), python-picard, scikit-learn, psychopy, PySide6, pylsl, sounddevice, praat-parselmouth, and, on Windows only, pycaw and comtypes (used to set the system volume). No version is constrained except those of fooof and praat-parselmouth.

  1. Get the code and create an environment.

  2. Run the tests. The README says they are "Fast checks that do not require EEG or audible playback":

Python version and PsychoPyThe repository does not state a Python version. PsychoPy is the most demanding dependency (it plays the sounds and reads the keyboard); check its own installation instructions for the Python versions it supports before creating the environment. The recording engine's header recommends the Psychtoolbox audio backend for "the best onset precision" (pip install psychtoolbox, oddball_paradigm_with_lsl.py, lines 55 to 57), and asks to run sessions "from a plain terminal ... with other heavy applications closed".
Probable problem with NumPy 2.4 or laterThe signal check computes band powers with np.trapz (portiloop_setup.py, line 203). NumPy removed this function in version 2.4: "numpy.trapz: deprecated since NumPy 2.0 (2023-08-18). Use numpy.trapezoid or scipy.integrate functions instead." [5]. Because the requirements do not pin NumPy, a new installation may get 2.4 or later, and the channel metrics of the signal check would then fail. We did not run it; if you see an AttributeError about trapz, installing a NumPy older than 2.4 should avoid it (untested).

Operating systems. The README and code mention Windows, macOS and Linux. When you select an audio output, the console fixes the task's stream gain at 50% and asks the operating system to set its output volume to 50% (README lines 470 to 473): with osascript on macOS, through pycaw on Windows, with pactl or wpctl on Linux (tmda_pav/audio/system_volume.py). If it cannot verify the level, it asks you to set it by hand. On Windows the output list uses "the same WASAPI endpoint view that PsychoPy uses for playback" (README line 475).

  • Subject ID: the participant. Generate participant ID... creates "a short random ID containing the selected collection laptop's stable letter, such as A7KMP" (README lines 457 to 459). Never use names.

The identifier lists themselves are stored as one small file per change in Shared/id_events, so that several laptops working offline do not overwrite each other (README lines 441 to 455).

The signal-quality console

Before recording, run the signal check (task "Portiloop signal check", portiloop_setup.py). Its docstring is explicit about what it is:

"Live, waveform-based setup checks for the FatigueMMN Portiloop montage. The monitor reads the LSL stream without modifying or recording the MMN task. It does not measure electrode impedance."portiloop_setup.py, lines 12 to 14 [1]

So the impedance check stays in the Portiloop's Check tab (tutorial 03). The add-on's console shows, for the selected electrodes, the last 10 s of traces (optionally filtered: defaults high-pass 1 Hz, low-pass 40 Hz, notch 60 Hz, montage.py, lines 22 to 26), a power spectrum over 30 s, and a table of metrics per channel computed on the last 2 s (drift on the last 10 s). The flags come from fixed rules (compute_channel_metrics, lines 209 to 353):

In a 50 Hz countryThe line-noise rule looks only at 58 to 62 Hz. Where the mains are at 50 Hz (as in the CLAS protocol of tutorials 01 to 05), it will not flag mains noise; look at the spectrum yourself, and set the display notch to 50 Hz in the montage editor's filter settings.

Three guided checks record a short, instructed segment (CHECK_DEFINITIONS, lines 173 to 189):

  • Quiet check (20 s): "Relax, look forward, and remain as still as possible." It reports how many channels are flagged.
  • Blink check (12 s): "Blink firmly three times, with a short pause between blinks." It compares the range of EOG1 minus EOG2 with the quiet check (it needs two channels of type EOG).
  • Eyes-closed check (20 s): "Close your eyes, relax, and remain still until the countdown ends." It compares the 8 to 13 Hz fraction at a channel named Pz with the quiet check, and says itself: "this is supportive, not pass/fail."

Save QC Report writes setup_quality_<time>.json, a channel CSV and trace and spectrum images in the session folder; the JSON records the montage, the filters, the stream and the guided checks, with the sentence "Waveform-based signal plausibility only; no electrode impedance or contact resistance was measured." The experiment console can warn before a recording if no report matches the identity and input map (this warning is "opt-in under EEG montage", README line 97).

The current version also has an Oscillations tab (band RMS over the last minute, in 1 s windows), a scalp topography that needs MNE, and a "Separate periodic / aperiodic" option, which the README calls "an exploratory live estimate, not the offline FOOOF peak model" (lines 89 to 115). The Portiloop EEG button at the top of the experiment console opens the same monitor without asking for identifiers and without saving.

The standalone signal check

The README describes a "generated single-file copy of the setup console", dist/portiloop_setup_standalone.py, built by python tools/build_portiloop_setup_standalone.py, that needs only Python and five libraries (numpy, scipy, matplotlib, PySide6, pylsl) and opens "without requesting Environment, Subject, or Session IDs" (lines 136 to 160). The dist/ folder is not in the repository (it is ignored by .gitignore): you build the file yourself.

The Portiloop repository contains such a file, examples/portiloop_check_standalone.py, with examples/portiloop_check_standalone_requirements.txt. We compared it with the add-on's sources, without running either: it is a build from an earlier version. It embeds 7 modules where the current build script lists 13; it has no Oscillations tab, no periodic/aperiodic option, no "Hardware REF" setting (it always writes TP9) and no quick monitor mode; and its embedded modules do not carry the license header lines. Its traces, spectrum, metrics table, guided checks and QC report follow the same rules as above. If you need the features described in the README, build the standalone from the add-on's repository.

Re-referencing after the recording

Every Portiloop channel is recorded against the REF electrode. The utility EEG utility: montage and reference (eeg_montage.py) writes a re-referenced copy of a FIF file, never the original (docs/eeg_reference.md). It follows MNE's procedure: the original reference is added back as a channel of zeros, then the mean of the selected electrodes is subtracted from every EEG channel.

"Each EEG channel is then transformed by subtracting the mean of the selected electrodes. Thus the recovered Cz becomes `Cz - mean(TP9, TP10)`, not an absolute potential measurement. ... An arbitrary unmeasured scalp electrode cannot be recovered this way."docs/eeg_reference.md, lines 26 to 31 [1]

With the default wiring (REF on TP9, TP10 recorded on CH1), choosing TP9 and TP10 as the new reference gives each electrode minus the mean of the two mastoids (the restored TP9 is zero, so the subtraction is half of TP10). The copy is saved beside the source as, for example, subject_ref-mean_TP9_TP10_raw.fif with a .reference.json audit file; EOG, ECG, EMG and trigger channels are unchanged and no filtering is applied.

For neuroscientistsThe MMN is usually largest at fronto-central sites and inverts in polarity at the mastoids when the nose or an average reference is used [6]; a mastoid reference therefore reduces part of the fronto-central MMN. Decide the reference before analysing, and use the same one for every participant: the analyses do not re-reference by themselves (the P1-N1-P2 provenance says "reference": "unchanged from main MMN preprocessing").

Sound level: output, baseline and sensation level

The tasks need three things that the console checks at launch (experiment_console.py, lines 2950 to 3010):

  • A fixed audio output: the stream gain is 50% (DEFAULT_AUDIO_VOLUME_PCT = 50.0) and the system volume is set to 50%. Keep the operating-system and headphone volume unchanged between calibration and tasks (README "Troubleshooting Order", line 600).
  • A quiet-room baseline recorded with the selected microphone (Record quiet baseline, 10 s by default, 1 to 300 s). Every EEG task also records the microphone in parallel, and the sound level above that baseline becomes FIF annotations such as SOUND_ABOVE_BASELINE_10_20_DB. The levels are "dBFS (digital full scale), not absolute dB SPL" (README lines 479 to 490).
  • A sensation-level (SL) calibration for the subject in this environment (task "SL calibration", sl_task.py). The participant hears a 200 ms burst every second and adjusts it with the arrow keys, in 2 dB steps from -60 dBFS, "until they can just barely hear it (detection threshold), then confirms with SPACE" (sl_task.py, lines 18 to 20). The task level is set 40 dB above that threshold by default (capped at 0 dBFS, with a warning), and the result is saved as sl_calibration.json in the subject folder. This is a single method-of-adjustment estimate, not a staircase.
Calibrate with the sound you will useBy default the SL task uses white noise ("noise_type", "Noise color", "white", task_protocols.py, line 74), while the MMN stimuli are pink noise (multifeature.py, line 61). The README itself says: "Changing a sound's spectrum, RMS, or duration can change its hearing threshold; redo SL calibration with a representative stimulus and the same sound output." (lines 222 to 223). Set the SL protocol's noise colour to pink if you use the default MMN sounds, or check with the author which was used for the published data.

Audio latency: why and how it is measured

The laptop knows when it asked for a sound, not when the sound reached the ear. Between the two there are the audio buffers of the operating system and the sound card; and between the sound at the ear and the time stamp of the EEG sample that contains the response there is also the acquisition and streaming delay of the Portiloop. An ERP is an average of epochs cut at the event times: a constant error in those times shifts every latency you measure, and a variable error also smears and flattens the average. The add-on measures the whole chain once per laptop and output, and adds the mean to every auditory event time.

How it measures it. The task "Computer audio latency calibration" (audio_latency_task.py) plays a pink-noise burst, records pylsl.local_clock() "immediately after PsychoPy Sound.play" as the trigger time, and looks for the first electrical transient of that sound on a Portiloop input, in the same LSL stream and time stamps as the EEG (tmda_pav/tasks/audio_latency.py, lines 842 to 910). For this, the headphone output is wired, through an attenuator, to an electrode input. Its defaults:

The accepted result, with the mean, median, standard deviation and range of the delays, is saved as Data/_laptops/<Laptop ID>/audio_latency.json, with the instruction "Add mean_delay_ms to software sound-trigger timestamps before ERP epoching." Every run (accepted or not) keeps its trials, raw EEG and a summary figure under latency_runs/.

Safety: no participant on the loopback"This is an electrical fixture test only: no participant may be connected, and the headphone output must be appropriately isolated or attenuated before it is connected to an EEG input." (README lines 511 to 513). The task asks you to confirm "I confirm that no participant is connected and the test connection is safe." The repository does not describe the fixture (connector, attenuator values); we do not know what the author used, so ask before building one.

How it is applied. In the MMN tasks every sound's event time is actual_onset = pylsl.local_clock() + AUDIO_LATENCY_SEC, taken right after snd.play(), the same definition of the trigger as in the calibration (oddball_paradigm_with_lsl.py, lines 2583 to 2589), and AUDIO_LATENCY_SEC is the calibration's mean_delay_ms for this laptop, output, backend and gain (lines 906 to 924). Reaction times are measured from that corrected time. If no matching calibration exists, the console asks before launching and the task uses zero correction; every FIF records what was applied (TMDA_PAV_AUDIO_LATENCY_JSON in its description). Older recordings can be corrected afterwards, into a new file, with EEG utility: apply laptop audio latency or update_audio_latency.py ... --assume-uncorrected (README lines 522 to 542).

What a delay does to an ERP, and what the correction can and cannot fix

What to try: raise the delay and watch the uncorrected average move later; raise the trial-to-trial jitter and watch every average become smaller and wider, corrected or not. Illustrative: the "true" response is an invented P1-N1-P2 shape and the delays are example values, not measurements of any laptop.

The widget shows the two parts of the problem. The constant delay is what the calibration measures and removes. The jitter (the part of the delay that changes from sound to sound) cannot be removed by adding one number: it widens and lowers the average, which is why the calibration warns when the delays span more than 10 ms. Two limits of the measurement itself: the EEG is sampled every 4 ms at 250 Hz, and a filter applied forward and backward spreads a sudden change both later and earlier in time, so the first threshold crossing of the filtered trace may come slightly before the true onset. The repository does not quantify this, and we have not measured it.

The tasks

All recorded tasks run in a PsychoPy window, record the Portiloop stream in a background thread, write everything to a live SQLite recovery file at least once per second, and can be resumed after an interruption ("Resume", "Start new" or "Cancel"; README lines 544 to 563). The parameters come from presets: each task has Default settings, and you can save your own under Shared/protocols/<task-kind>/. The defaults below are those of task_protocols.py, lines 48 to 119 and multifeature.py, lines 46 to 88; the repository contains no other preset file for these tasks. The parameters of each run are frozen in task_parameters.json.

Active and passive gap-deviant MMN

The mismatch negativity (MMN) is a negative deflection of the ERP to a sound that breaks a regularity of the preceding sounds; it is recorded with an oddball sequence of frequent "standards" and rare "deviants" and is visible as the deviant-minus-standard difference wave [6]. Here every sound is a 200 ms burst of pink noise; a deviant is the same burst with a short silent gap starting 100 ms after its onset.

ParameterActive MMNPassive MMN
Soundpink noise, 200 ms, RMS 0.20 before level scaling, 1 ms raised-cosine onset and offset ramps
Deviantsdev5, dev10, dev15: silent gap of 5, 10 or 15 ms starting at 100 ms, with 1 ms linear ramps on each side (min(1, gap/4) ms)
Stimulus onset asynchrony600 ms (200 ms sound, 400 ms silence)
Standards before each deviant1, 2 or 3 with probabilities 35%, 40%, 25%; so deviants are never adjacent
Deviant balanceblocks of 6 deviants, 2 of each type, shuffled
Duration900 s: round(900 / 0.6) = 1,500 sounds (or a trial count, if set)
Blocks and breaksevery 180 s: 300 sounds, 5 blocksevery 300 s: 500 sounds, 3 blocks
Habituation10 standards at the start of every block, marked and excluded from analysis
ResponseSPACE when a change is heard; a hit is the first press 0.1 to 1.0 s after a deviant; every other press is a false alarmnone: "Listen to the sounds without making a response."
Rapid QC at the endyes; optional 180 s extensions

The sequence is built by build_trial_sequence and build_blocked_trial_sequence: within each block, after the habituation standards, it repeats "draw a run of 1 to 3 standards, then take the next deviant from a shuffled block of six". The expected run length is 1 × 0.35 + 2 × 0.40 + 3 × 0.25 = 1.9 standards, so about 1 sound in 2.9 (34%) is a deviant. With our own re-implementation of these two functions (not the add-on's code) and 2,000 random draws, the active task has on average 498.5 deviants (476 to 516), about 166 of each type, among its 1,450 non-habituation sounds; the passive task 506.0 (485 to 525) among 1,470. The order of operations when the deviant is built matters: noise, outer ramps, RMS normalisation, then the gap, then the calibrated level; the gap is "deliberately inserted after normalization", because renormalising "would raise the level of its remaining noise and add a second cue besides the gap" (README lines 578 to 591).

The active and passive tasks are preceded, in the console, by Active MMN training (oddball_active_training.py): examples of each sound (2 repetitions by default) and 25 s of response practice with feedback, without EEG recording. At the end of an MMN recording, a rapid MMN review computes, while the EEG keeps recording, each deviant's mean difference in the 100 to 250 ms window at mean(Fz, Cz, FC1, FC2), its retention and its standardised measurement error (SME, Luck and colleagues' measure of the precision of a score [7]); the experimenter can then "stop and save or continue recording an additional extension" (README lines 396 to 403; defaults in multifeature.py, lines 81 to 87: SME criterion 0.5 µV, at least 10 clean pairs per deviant; band-pass 1 to 25 Hz, oddball_paradigm_with_lsl.py, lines 281 to 282).

For neuroscientistsFor a gap deviant, the deviance begins at the gap, 100 ms after the sound onset, and all epochs are time-locked to the sound onset. The offline MMN window, 150 to 250 ms after onset (erp_metrics.py, lines 16 to 17), is therefore 50 to 150 ms after the gap. The 5 ms gap is described in the engine as "near/below perceptual threshold for most listeners", the 15 ms gap as "clearly audible" (lines 235 to 237); the active task's hit rates per deviant tell you how detectable each one was for each participant. Note also that with about one deviant in three sounds (each deviant type about one in nine), deviants are more frequent here than in a classic oddball.

Eyes-closed resting state

resting_state.py records an eyes-closed rest of 180 s by default, after preparation screens (devices, posture, relaxation, blinking). The participant reads "Close your eyes now and sit quietly. Try not to move or blink. Keep your eyes CLOSED until you hear the gong." and a gong ends the rest (run_resting_state, lines 622 to 669). The gong is assets/rest_end_gong.wav by default, played at 40 dB above the participant's threshold. (The file assets/GONG_FILE_INSTRUCTIONS.txt says 28 dB SL, "12 dB below the 40 dB SL MMN stimulus setting"; the code's default is 40 dB SL. It also asks you to confirm that the WAV's license permits its use.) The rest is saved as <subject>_<session>_<run folder>_rest_pre_raw.fif; give the runs the suffixes pre and post to have them compared.

The sequencer

The Sequence tab of the console stores an ordered list of steps, each with its task, its save suffix and an embedded copy of its parameters, saved as JSON under Shared/protocols/sequences. The example in the repository is a pre/post design:

{"name": "Example pre-post experiment",
 "steps": [{"task_key": "rest",            "suffix": "pre"},
           {"task_key": "active_training", "suffix": "pre"},
           {"task_key": "active",          "suffix": "pre"},
           {"task_key": "rest",            "suffix": "post"}]}

When you press Start sequence, the selected environment, subject, session, laptop, audio output and microphone are fixed for the whole sequence; each step goes through the same checks as a single launch (calibration, baseline, signal check, audio latency, resume); a step that fails or is interrupted stops the sequence "instead of skipping ahead"; Start from selected step resumes from a chosen step (README lines 162 to 198). The signal check is not a step: it is "a parallel setup tool rather than a bounded experiment step". Each Session ID is associated with one saved sequence.

This has NOT been verified per-channel" (its value is 1.0; lines 207 and 215 to 217). Since the Portiloop already streams microvolts, a factor of 1.0 leaves them unchanged.

The analyses

Analyses run from the Analysis tab of the console (a recording table where you tick the files) or from the command line, for example python mne_analysis.py --select --database-dir /path/to/Data. Each run creates a new folder Data/_derivatives/<analysis-name>/<UTC-timestamp>_<token>/ with subjects_summary.csv (exactly one row per Subject ID, with columns per suffix, environment and session), recordings.csv, summary_columns.json, analysis_run.json and one folder per recording; nothing earlier is overwritten (README lines 243 to 287). Read the subject column as text, as the README recommends: pd.read_csv(path, dtype={"subject": str}).

MMN ERP and time-frequency (mne_analysis.py)

  1. EOG1 minus EOG2 as a derived EOG channel; band-pass 1 to 25 Hz; Picard ICA to remove EOG-linked components when found (recordings of at least 30 s);
  2. epochs -200 to +600 ms around each sound, linear detrend, baseline -200 to 0 ms;
  3. rejection of epochs above 100 µV peak-to-peak on EEG or 500 µV on the derived EOG;
  4. averages per condition; difference waves "Each deviant minus all retained STANDARD and STANDARD_PRE trials (habituation standards excluded)" at mean(Fz, Cz, FC1, FC2);
  5. signed area and peaks in the MMN (150 to 250 ms) and P3 (250 to 350 ms) windows; Morlet time-frequency power from 4 to 25 Hz; first and second halves and per-block measures with SME, split-half waveform correlations over 50 to 350 ms and a bootstrap interval of the change (500 repetitions, fixed seed).

Source: docstring, lines 8 to 52 and settings, lines 103 to 120.

P1-N1-P2 to standards (mmn_standard_erp_analysis.py)

The same preprocessing and epochs; the standards (and, separately, all stimuli) excluding habituation; local-peak amplitudes and latencies, window means, signed area and P1-to-N1 and N1-to-P2 peak-to-peak values at each electrode and at the cluster. Default windows (analysis_presets/mmn_erp_scoring.json): P1 30 to 80 ms, N1 80 to 150 ms, P2 150 to 250 ms, MMN 150 to 250 ms, P3 250 to 350 ms; "These windows are configurable, not universal physiological definitions." A peak needs two samples decreasing away on each side, following McArthur and colleagues [8] (README lines 345 to 371).

Active MMN behaviour (mmn_behavior_analysis.py)

Hit rate, reaction time and d' overall, per block and per deviant. d' uses the log-linear correction of all four cells, hit rate (hits + 0.5)/(signals + 1) and false-alarm rate (false alarms + 0.5)/(noise trials + 1) (mmn_behavior.py, lines 41 to 47; Hautus [9]). A false alarm counts "only once per eligible standard". Passive recordings are excluded.

Resting state (mne_analysis.py --rest)

EEG band-pass 1 to 70 Hz and a 60 Hz notch; 4 s windows with 2 s overlap, rejected above 500 µV; Welch spectra; band power delta 1 to 4, theta 4 to 8, alpha 8 to 13, beta 13 to 30, gamma 30 to 55 Hz at Fz, Cz and Pz; the ratio Fz theta / Pz alpha; band RMS in 1 s windows over time; a FOOOF fit (fixed aperiodic mode, 1 to 55 Hz) for periodic band power and the aperiodic exponent; and pre/post differences within session when runs have the suffixes pre and post (mne_analysis.py, lines 139 to 161).

The resting-state notch is fixed at 60 HzREST_NOTCH_HZ = 60.0 (line 149) has no command-line option. At a 50 Hz site, the mains frequency falls inside the gamma band (30 to 55 Hz) and inside the 1 to 70 Hz band-pass. Change this constant (and check the gamma results) before analysing 50 Hz recordings.

Statistics

The README summarises:

"Permutation reports give two-sided sign-flip p-values and Benjamini-Hochberg adjusted p-values across component/condition tests within each report (within each context for pre/post). They assume exchangeable signs under the null; strong serial dependence or order effects warrant caution. These are window-level tests, not evidence that an individual peak or time point is significant."README.md, lines 80 to 85 [1]

In the code (tmda_pav/analysis/erp_permutation.py; SciPy's permutation_test, 4,999 resamples, seed 2026; false discovery rate with mne.stats.fdr_correction, whose default is the Benjamini-Hochberg procedure [10]):

  • P1-N1-P2: within each recording, the trial window means of a component are tested against zero by sign flips.
  • MMN, within a recording: the deviant trials' window means are compared with the window means of all retained standards by permuting the condition labels ("Independent-label permutation, not sign flips of shared-reference trials", line 17), for each deviant and for all deviants pooled, in the MMN and P3 windows.
  • MMN, group pre/post ("Create MMN grand average and matched pre/post CI95 plots"): participants with both pre and post; pointwise Student-t 95% intervals across participants ("not simultaneous bands"), and sign-flip tests of post minus pre per participant.
README and code disagree on the MMN referenceThe README says the paired permutation CSV tests each deviant "using its own preceding retained standard in the same block" (lines 65 to 67), that halves and blocks pair "each deviant ... with its immediately preceding non-habituation standard" (lines 324 to 326), and that the rapid review analyses each deviant "against its immediately preceding standard" (lines 397 to 398). The code at this commit does otherwise: the reference is the mean of all retained standards excluding habituation (REFERENCE_METHOD = "all_retained_task_standards_excluding_habituation", mmn_reference.py, lines 8 to 23), used by the halves and blocks, the rapid review and the permutation test, and the within-recording MMN test permutes labels rather than flipping signs. Report the method from the code (and the commit) in a paper, or ask the author.

These are tests within one recording (are this participant's deviant trials different from their standards?) or, for pre/post, across participants. For a group study, the usual approach is to take one value per participant and condition from subjects_summary.csv and test it across participants, as in tutorial 09.

A session, step by step

  1. Once per laptop and audio output: run the audio-latency calibration on the loopback fixture, with no participant.
  2. Once per environment: create the Environment ID and record the quiet baseline with the microphone you will use.
  3. Participant: generate or select the Subject ID and Session ID; place the electrodes; set the montage if the wiring differs from the default.
  4. Portiloop: Check tab with all electrodes, "Acquisition only", "Stream LSL", Start (above).
  5. Signal check: traces and flags, the three guided checks, Save QC Report.
  6. SL calibration (once per subject and environment), with the stimulus you will use.
  7. Tasks: launch them one by one, or start the session's sequence. Do not touch the volume.
  8. End: Stop on the Portiloop after the last task; copy Data (and the Portiloop's CSV backup, if any).

Exercises

Counting trials

With the default active MMN settings, how many sounds are played, how many blocks are there, and roughly how many deviants of each type? How do the numbers change for the passive task?

Answer

Active: round(900 / 0.6) = 1,500 sounds, blocks of round(180 / 0.6) = 300 sounds, so 5 blocks and 50 habituation standards. About 1 sound in 2.9 of the remaining 1,450 is a deviant: about 500 deviants, about 166 of each type (our re-implementation gives 476 to 516 over 2,000 draws). Passive: also 1,500 sounds, but in 3 blocks of 500, so 30 habituation standards and about 506 deviants. Breaks and the rapid review add time to the 15 minutes of sounds.

Overnight wiring for a wake session

A participant comes for a wake session wearing the CLAS overnight montage (tutorial 02). What must you change in the Field Console before recording, and which parts of the signal check and of the analyses will not work?

Answer

In Edit EEG montage...: CH1 ECG1 and CH2 ECG2 (type ecg), CH3 EOG1 and CH4 EOG2 (type eog), CH5 EMG (type emg), CH6 Cz, CH7 Fz, CH8 Fpz (type eeg), and the Hardware REF field set to the right mastoid (TP10 in 10-10 names). Then run a new signal check. The blink check works (two EOG channels); the eyes-closed check does not (no channel named Pz). The MMN cluster becomes mean(Fz, Cz), since only the existing names are used; the resting analysis has no Pz, so the Fz theta / Pz alpha ratio is not available. The recording keeps its input map in recording_montage.json.

A forgotten calibration

You recorded three participants on a new laptop before running the audio-latency calibration. What did the add-on do with the event times, and how do you fix the recordings?

Answer

Without a matching calibration the console asks before launching and, if you continue, the task uses zero correction; the FIF records that no correction was applied. Run the calibration with the same laptop, output, backend and gain, then use EEG utility: apply laptop audio latency (or update_audio_latency.py), which writes a new _latency_<value>ms_raw.fif with the annotations and STI 014 markers shifted by the new correction minus the previous one. Files without the audit metadata need --assume-uncorrected. The originals are kept.

A site with 50 Hz mains

The study runs where the mains are at 50 Hz. List what you would change or watch in the Field Console.

Answer

Set the display notch to 50 Hz in the montage editor's filter settings; do not rely on the "60 Hz dominates" flag, which looks only at 58 to 62 Hz, and inspect the spectrum instead; change REST_NOTCH_HZ in mne_analysis.py to 50 before the resting-state analysis (otherwise 50 Hz mains fall in the gamma band and inside the 1 to 70 Hz band-pass). The MMN analysis is low-passed at 25 Hz, so the mains matter less there. The Portiloop's own notch setting does not change the raw stream used by the add-on.

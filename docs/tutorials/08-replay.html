Tutorial 08 · Processing the recordings

Replaying a night offline

The Portiloop software includes a simulator that feeds a recorded night, sample by sample, through the same filter, detector and stimulator code that ran on the device, in a few minutes. Use it to check what the device did, to see exactly what its detector looks at, and to try other settings on real data before a study.

In this tutorial you will

  • Learn what portiloop/src/simulator.py does and what it writes

What the simulator does

The simulator is a single script, portiloop/src/simulator.py. Its docstring says what it is for:

portiloop/src/simulator.py (docstring)"Replays recorded Portiloop CSV data through Portiloop processors, detectors, and stimulators faster than real time (as fast as possible), generating a new CSV with updated detection and stimulation markers, and optionally streaming via LSL."

For each row of the recorded CSV it does what the device does for each new sample, using the same Python classes. For the pipeline of the tutorial night, "Sleep slow oscillations (upstate)" (custom_pipelines.py, lines 28 to 33), these are:

  1. Raw row of the CSVraw_ch1 ... raw_ch8, µV
  2. SlowOscillationFilterFIR 0.5 to 30 Hz, notch, DC removal, FIR 0.16 to 4 Hz
  3. SOUpstateDetectorcriteria on the detection channel, up-state timing
  4. SlowOscillationStimulatorat most one sound per 0.1 s; sound disabled
  5. New CSV rowraw, filtered, detection, stimulation, stimulation_on, timestamp

To run this code on an ordinary computer, the script replaces what only exists on the device:

  • Hardware. The libraries periphery, spidev and alsaaudio are replaced by dummy modules when they are not installed, and the ADS1299 backend by a mock that reports 8 channels.
  • Sound is switched off: "Disable sound card playback to run at maximum computational speed" (simulator.py lines 500 to 502: the stimulator's play_sound is replaced by a function that does nothing).
  • Time. The code of the stimulator reads time.time() (for example to keep 0.1 s between sounds). The simulator replaces it by a simulated clock that follows the recording: the time of row i is i / 250 s, because device CSVs have no timestamp column (line 553).
  • The "Stimulation starts after" delay (sleep_timeout, from the metadata) is counted in samples: detection and stimulation start at exactly 25 min for the tutorial night (lines 559 to 570).

It writes two files. The CSV has the header (lines 207 to 209) raw_ch1..8, filtered_ch1..8, detection, stimulation, stimulation_on, timestamp: the raw values copied from the input, the device-filtered signal of every channel (which the device itself does not save, since "record_filtered": false), the new markers and the time in seconds. Next to it, <output name>_metadata.json holds the configuration used (the input's metadata, the command-line overrides, and the pipeline name).

On the hard driveInput: <name>.csv, plus <name>_metadata.json found automatically next to it. Output, by default next to the input: <name>_simulated.csv and <name>_simulated_metadata.json. The output CSV is large: 1.7 GB for the 7.4 h tutorial night (the recording itself is 585 MB), because it adds eight filtered columns at full precision. Nothing is written to the device and no sound is played.

Running it

  1. Get the code. Clone portiloop-software (branch main, the Portiloop v2.3 software). To reproduce the tutorial night exactly, check out the version that recorded it with git checkout 917f1f3; the current main includes the fix described below. Run the commands below from the repository folder, with a Python that has numpy and scipy installed. Nothing else is needed for a slow-oscillation replay: we ran the simulator of branch main on a computer without the device's packages, and the hardware libraries it lacks are replaced automatically (see above).
  2. Run it. For the tutorial night, with the settings of its metadata: 
    python portiloop/src/simulator.py -i clas-tutorial_2026-11-15_04-01-29_CONDB/clas-tutorial_2026-11-15_04-01-29_CONDB.csv -o simulated.csv -q
    The whole 7.4 h night took 3 min 8 s on a desktop computer, about 140 times faster than real time. Importing the package first tries to play a start-up sound (portiloop/src/__init__.py line 17 runs aplay on sample1.wav at a path of the device); on a computer it prints an error such as sample1.wav: No such file or directory, which you can ignore. Without -q the script prints a progress line and a summary. Here is the summary of a one-minute excerpt of the night (minute 123 to 124) replayed with --sleep-timeout 0:

Known issue: -p "Sleep spindles" is ignoredThe default of -p is "Sleep spindles", and the script uses the metadata's pipeline whenever -p equals that default (if pipeline_name == "Sleep spindles" and pipeline_from_meta:, line 290). So asking explicitly for -p "Sleep spindles" on a slow-oscillation recording silently replays the slow-oscillation pipeline (we checked: the log says Pipeline: Sleep slow oscillations (upstate)). Use the alias -p spindles instead, and always read the Pipeline: line of the log. Note also that the spindle pipeline needs a neural-network runtime on your computer (tflite_runtime or TensorFlow); without one it stops with "TensorFlow or tflite_runtime is required to run SleepSpindleRealTimeDetector." We did not test a spindle replay.

Evaluating a code change on a recorded night

Because the replay is exact, it can measure what a change of the code does to a real night. The version that recorded the tutorial night truncated the detector's estimate of the up-state delay to an integer at every update (custom_detectors.py line 267):

                        # compute a running average
                        self.est_t_upstate = int(self.alpha * self.t_upstate + (1 - self.alpha) * self.est_t_upstate)

This was fixed on main on 26 November 2026 by commit e4959f1, whose message explains the effect: "The running average of the time from the upward zero crossing to the up-state peak was truncated to an integer at each update, so it settled 4 to 5 samples (16 to 20 ms) below the average and the stimulations came early. It is now kept as a float." The fixed code keeps the estimate as a float and compares the counter with round(self.est_t_upstate).

Replaying the tutorial night with the fixed version (e4959f1) gives 1,918 stimulations (1,888 before the device stopped, plus the same kind of extra stimulations after minute 401). 1,874 of the 1,930 recorded stimulations have a replayed one within 25 samples, and almost all of these come 3 to 6 samples (12 to 24 ms) later: 3 samples for 182 pairs, 4 for 882, 5 for 692 and 6 for 109; 9 pairs have 1, 2 or 7 samples. The estimate itself moves from a median of 46.0 samples (917f1f3) to 50.8 samples (e4959f1), and the mean phase of the 0.5 to 2 Hz oscillation at the stimulation (as computed in tutorial 07) from -16° to -11°: closer to the up-state peak (our computations).

Note the software version of every study nightThe tutorial night was recorded before the fix: its stimulations came about 16 to 20 ms early. Devices updated after 26 November 2026 stimulate later by about that amount. If a study has nights recorded before and after an update, the timing of the stimulation differs between them. Write down the software version (the commit) of each device for each night; the software_version field of _metadata.json ("0.2.0" for the tutorial night) does not identify the commit. A replay with both versions, as here, tells you how large the difference is on your own data.

One caution: the fixed replay places its markers on an EEG that was recorded with the original stimulations, so it tells you where the new code would have stimulated, not how the brain would have responded (below).

What the detector sees

The replay gives something the device does not save: the filtered signal on which the detection runs (filtered_ch6 for Cz). The upstate detector uses fixed criteria on that signal, in µV and ms; they are not adaptive and not shown in the Control Center:

        self.th_PaP = 75  # total amplitude threshold
        self.th_Neg = 40  # negative amplitude threshold
        self.min_tNe = 125  # minimum duration spent below 0 (in ms)
        self.max_tNe = 1500  # maximum duration spent below 0 (in ms)
        self.max_tPo = 1000  # maximum duration spent above 0 (in ms)

How they are used (run_detection, lines 214 to 288):

  1. A wave starts at a downward zero crossing. From there the detector tracks the highest and lowest values and the time spent below and above zero.
  2. The criteria hold when the peak-to-peak amplitude exceeds 75 µV, the lowest value is more than 40 µV below zero, the time below zero is between 125 and 1500 ms, and the time above zero is under 1000 ms.
  3. At the upward zero crossing a counter starts. Each time a wave that met the criteria ends (next downward crossing), the detector updates its estimate of how many samples separate the upward crossing from the positive peak: est_t_upstate = int(0.1 * t_upstate + 0.9 * est_t_upstate) in the version that recorded the night (without int after the fix).
  4. It detects on the single sample where the counter equals the estimate, if the criteria still hold. That is the predicted up-state. The first qualifying wave after each Start only sets the first estimate and triggers no sound.

On the tutorial night (replay with 917f1f3) the estimate had a median of 46 samples (184 ms) over the 1,960 replayed stimulations, and a 5th to 95th percentile range of 22 to 73 samples (88 to 292 ms). Note what is not in the criteria: there is no upper limit on amplitude. A movement artifact or a detached electrode that produces a large negative-then-positive swing passes them.

The detector in this widget is a line-by-line JavaScript copy of run_detection, in both versions. We checked it: with the device values, the 917f1f3 version reproduces the device's and the replay's detections at the same samples in all three excerpts (17 detections, 13 of them recorded by the device), and the e4959f1 version reproduces the fixed replay. The Python copies in the data script reproduce all the detections and stimulations of both whole-night replays, sample for sample.

For neuroscientistsThe criteria are amplitude thresholds on one channel, after causal filters that keep roughly 0.5 to 4 Hz and delay a 1 Hz wave by about 39 ms (our computation from the filter coefficients). They do not look at sleep stage, at the EOG or EMG, or at an upper amplitude limit. That is why, on the tutorial night, stimulations also occur in periods the automatic staging calls W (tutorial 06), and why every analysis must reject artifacts afterwards (tutorial 07). The thresholds are absolute values in µV: an electrode with a different impedance, a different position, or an older participant with smaller slow waves will change how many waves pass them.

What the simulator does not simulate

  • The lead-off pause. On the device, when the detection electrode comes off, detection and stimulation are paused for the rest of the recording (tutorial 04); on the tutorial night stimulation_on drops to 0 at minute 373.36 and never comes back. The simulator has no lead-off detection: its stimulation_on only reflects the sleep timeout. It keeps "stimulating" until the end: 30 stimulations between minutes 401.7 and 428.3, on swings of thousands of µV from detached electrodes (the "after" excerpt in the widget above). If you analyse a replay, cut it where the device stopped, or apply the _leadoff.json of the original recording.
  • The device clock. On the device, time comes from the system clock and the acquisition loop; in the replay, sample i is at i / 250 s exactly. One visible consequence: the device started detecting at minute 25.04, the replay at 25.00, because the Control Center checks the "Stimulation starts after" delay every 10 s (ui.timer(10, exp_state.check_sleep_timeout), simple_gui.py line 730), whereas the simulator counts samples. On this night no slow wave was detected in those 2.4 s, so the stimulations are unaffected. The replay also assumes that every row comes exactly 4 ms after the previous one; the device's timing irregularities (such as the lost samples counted in _stats.json) are invisible to it.
  • The sound. Nothing is played, and the audio latency of the device is not modelled.
  • The brain. The replayed EEG is the one recorded with the original stimulations. It contains the responses to the sounds the device actually played, at the device's times. If you replay with other settings or other code, the new markers fall on a signal that was shaped by the old ones.

What it is useful for

  • Checking a recording. Replay the night with the same software version and compare the markers, as above. An exact match tells you that the recorded markers are those of the configured pipeline on this signal. A partial match tells you that something differs: the settings, or the version of the code.
  • Evaluating a code change, as in the example above: replay the same nights with the old and the new version and compare when they stimulate.
  • Seeing the detection signal. filtered_ch* lets you look at what the detector saw around any stimulation, or around a slow wave it missed.
  • Testing settings before a study. Replay a pilot night with another detection channel (-c 7 for Fz), the notch your site needs (--power-line 50), stimulation delays (--min-delay, --max-delay, --inter-stim-delay), another "Stimulation starts after" value, or another pipeline (-p so, -p spindles), and count how many stimulations you would get and when. The fixed thresholds of the detector are not command-line options: changing them means changing the code.
  • Checking that a pipeline behaves on your data, for example on recordings from a new population or a new electrode montage, before running the device with participants.
Use sham nights for offline testsBecause of the last point of the previous section, the cleanest data for testing settings offline are nights without sound: Cond A (sham) nights or nights recorded with "Acquisition only". Their EEG was not shaped by any stimulation. (Cond A files contain the sham markers, but the replay writes its own.)

Exercises

Tolerance

In the timeline widget, choose the replay made after the fix and set the pairing tolerance to 5 samples, then 2. How many pairs remain? What does it say about the effect of the fix? Then choose the replay made with 917f1f3 and set the tolerance to 0.

Answer

After the fix: 1,874 pairs at 25 samples, 1,762 at 5 samples, only 6 at 2 samples. Almost every pair is 3 to 6 samples apart: the fix moves the stimulations later by a nearly constant amount. With 917f1f3, all 1,930 recorded stimulations are paired even with a tolerance of 0 samples.

Thresholds

In the detector widget, artifact excerpt (minute 297.2), lower the peak-to-peak threshold to 60 µV. Then go back to the device values and raise the minimum time below zero to 250 ms. How do the detections change?

Answer

With the device values the detector stimulates 3 times here, as the device did. With a 60 µV peak-to-peak threshold, a smaller wave passes and it finds 4. With 250 ms below zero, only the longer down-states pass and it finds 2. These are 30 s estimates: the in-page detector starts from the state the real detector had at the start of the excerpt, and over a whole night the estimate of the up-state delay would also evolve differently. The device cannot be set this way from the Control Center: the thresholds are constants in the code.

A replay for a site with 50 Hz mains, on Fz

Write the command that replays a night with the notch at 50 Hz, detection on Fz (default montage), Cond A, writing night_fz.csv.

Answer

python portiloop/src/simulator.py -i night.csv -o night_fz.csv -c 7 --power-line 50 -C A. The condition only changes the log and the metadata, not the columns. Check the Pipeline:, Detection Channel: and Sleep Timeout: lines of the log.

After minute 401

Why does the replay stimulate between minutes 401.7 and 428.3 when the device did not, and how would you remove these stimulations from an analysis of the replay?

Answer

The electrodes had come off near minute 372.8, and the device's lead-off protection paused detection for the rest of the recording; the simulator does not model it, and the large swings of the detached electrodes pass the detection criteria, which have no upper amplitude limit. Keep only the replay's markers where the device's stimulation_on was 1, or use the _leadoff.json of the recording (with load_recording, epochs that overlap a lead-off period are rejected).
